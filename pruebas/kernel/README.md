# Pruebas del kernel sin AWS

Comprueban, ejecutando Strands de verdad, lo que el documento de arquitectura (`docs/arquitectura-agentes.md`, sección "Verified before building") afirma sobre su comportamiento. No llaman a Bedrock ni a ningún servicio de AWS: usan un modelo falso (`fake.py`) que devuelve respuestas preparadas y apunta lo que recibe, y servidores MCP mínimos y locales (`mcp_eco.py` por stdio; `mcp_cabeceras.py` por Streamable HTTP, que apunta la cabecera `Authorization` y la sesión de cada petición).

Están fijadas a las versiones que se han leído (Strands 1.63.0, SDK de AgentCore 1.25.2). Al subir de versión, se repiten: si alguna falla, el documento ha dejado de ser cierto.

```bash
cd pruebas/kernel
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest -q -s -p no:warnings
```

`test_limite_de_procesos_solo_vale_con_otro_usuario` solo comprueba la diferencia entre root y otro usuario si se ejecuta como root (y necesita el usuario `nobody`).

| Fichero | Qué comprueba |
|---|---|
| `t_basico.py` | El snapshot restaura el prompt de sistema guardado y hay que volver a fijarlo; `BeforeModelCallEvent.cancel` termina con `end_turn` sin llamar al modelo; registrar dos veces una herramienta (falla con `AgentTool` propias, no con `@tool`); `as_tool` exige `preserve_context=True` con snapshot. |
| `t_subagentes.py` | Ejecutor concurrente por defecto y secuencial con `SequentialToolExecutor`; un subagente consume los `Limits` del principal y sus llamadas al modelo no pasan por los hooks del principal; sus eventos llegan como `AgentAsToolStreamEvent`; el `cancel()` del principal también para al subagente; un hook de orden 0 ve la llamada antes que el `ask` de `HumanInTheLoop`, que solo recibe texto; herramientas registradas a mitad de ejecución. |
| `t_limites.py` | Los `Limits` por run paran con `stop_reason = limit_…` sin lanzar nada, tras terminar las herramientas pedidas; el mensaje siguiente cuenta de cero en el mismo `Agent` o restaurado del snapshot, y el modelo recibe el `toolResult` y ese mensaje como dos mensajes de usuario seguidos. |
| `t_grafo.py` | `Graph` no tiene `cancel()`; sus nodos comparten los `Limits` del principal solo si el grafo corre con su `invocation_context`; el `cancel()` del principal no para los nodos, y el de cada nodo sí: el grafo termina `FAILED` y el nodo siguiente no empieza. Hecha (2-11-2026): 4 de 4. |
| `t_contexto_sandbox.py` | Modo automático del contexto con stash en almacenamiento duradero (recorte, `retrieve_context`, snapshot pequeño, una entrada por bloque); `Graph` rechaza nodos con snapshot; la shell por defecto hereda el entorno y acepta el timeout del modelo; prototipo del `Sandbox` propio (entorno limpio, memoria, timeout fijo), y el límite de procesos, que como root no se aplica (por eso el `Sandbox` no pone ninguno). |
| `t_subagente_stash.py` | Un subagente `as_tool(preserve_context=True)` con el modo automático y el `storage=` del principal: su stash en `context/chat1/scopes/agent/revisor/`, aparte del principal, snapshot de 4,4 KB y `retrieve_context` tras montarlo de nuevo; lo recuperado no se vuelve a recortar (snapshot de 47 KB). Sin `storage=`, el stash va dentro del snapshot (85 KB); sin gestor de contexto, el snapshot lleva el resultado entero (81 KB). Hecha (2-11-2026): 3 de 3. |
| `t_backfill.py` | Saltar el backfill del stash al restaurar un chat (`_backfill_done = True` en el `ContextManager` tras montar el `Agent`): la primera llamada no lee el stash (con backfill, una lectura por bloque restaurado: 7 en un chat de 3 turnos), `retrieve_context` sigue recuperando un resultado recortado antes y los mensajes nuevos se siguen guardando en el stash; con un subagente `as_tool(preserve_context=True)`, igual marcándolo en los dos; falla si el atributo privado deja de existir. Hecha (2-11-2026): 4 de 4. |
| `t_memoria.py` | Memoria del usuario con el `MemoryManager` de Strands y un almacén propio que no escribe: con `search_tool_config=False` e `injection=False` solo se registra `add_memory`, la llamada llega al `add` del almacén (que deja la propuesta), la herramienta responde éxito (`{"stored": 1}`) y nada se pliega en el mensaje del usuario; tras restaurar el snapshot la herramienta sigue registrada. Hecha (3-11-2026): 2 de 2. |
| `t_mcp_meta.py` | El `approval_id` llega al servidor MCP en `_meta` solo en la llamada marcada, con un diccionario `meta` del `MCPClient` que rellena un hook. |
| `t_reutilizar.py` | El `Agent` del chat montado una vez y reutilizado en tres mensajes, cada uno con credenciales y token nuevos, sin reconstruir nada: todas las peticiones a Bedrock (principal y subagente `as_tool(preserve_context=True)`, `BedrockModel` real con la respuesta simulada en `before-send`) van firmadas con las credenciales del mensaje, leídas de un `Credentials` propio en la cadena del `boto3.Session`; todas las peticiones al MCP (principal y subagente) llevan el token del mensaje, puesto por un `httpx.Auth` propio (`auth_provider` del `MCPClient`); el `MCPClient` se conecta una vez y sigue abierto entre mensajes (con el protocolo 2026-07-28 sin sesión; con `initialize`, la misma `Mcp-Session-Id`, pero el stream GET se queda con el token del primer mensaje); el `SnapshotSessionManager` escribe tras cada mensaje también en el 2.º y 3.º `agent(...)`. Hecha (1-11-2026): 3 de 3, con mcp 2.3.0. Con Bedrock de verdad: `pruebas/aws/sonda_credenciales_vivas.py`. |
| `t_trazas_mcp.py` (+ `mcp_trazas.py`, `hub_trazas.py`, `trazas_fichero.py`) | Trazas a través del hub: kernel (Strands + `MCPClient` por Streamable HTTP, con los propagadores de AgentCore `baggage,xray,tracecontext`) → hub como el de la sonda 13 (proxy HTTP que lee el cuerpo) → MCP con el SDK 2.x. El `_meta` del kernel lleva el tramo `MCP send tools/call` del SDK de MCP (que cuelga del `execute_tool` de Strands y pisa lo que Strands inyecta), con `traceparent` y también `X-Amzn-Trace-Id`; el servidor MCP abre su tramo SERVER desde `_meta` sin configurar nada. Si el hub reenvía los mismos bytes, el MCP cuelga del kernel y el hub queda como hermano; si quita las claves de contexto (`traceparent`, `tracestate`, `baggage`, `X-Amzn-Trace-Id`) y escribe las de su tramo, el MCP cuelga del hub. Hecha (2-11-2026): 2 de 2, con mcp 2.3.0. Necesita `opentelemetry-propagator-aws-xray`. |
